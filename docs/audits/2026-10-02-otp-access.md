## Intended business rules and initial actual defects

Rules come from `docs/BUILD_SPEC.md` §9's emailed six-digit signing verification and the existing `tests/m7-signing.test.ts`: a ten-minute OTP and five-wrong-attempt lock. No new banking/legal/rate-limit policy is inferred. Operational security duration must remain independent of the demo's calendar offset.

**OTP-01 — High: concurrent wrong guesses undercount attempts.** Five actual `verifyOtp` calls each pause after a completed real signer read, then run their normal writes. Actual persisted attempts **1**, expected **5** and locked link. All five inputs are rejected but the lockout is bypassable. Test: “five concurrent incorrect OTP guesses persist five attempts and lock the link”.

**OTP-02 — High: stale correct verification bypasses an already committed lockout.** With four wrong attempts recorded, pause a correct code's signer read. Record the fifth wrong guess and confirm attempts5 through an independent DB context, then release the old correct read. Actual: verifies successfully, expected rejection and no verifiedAt. Test: “a correct OTP read before the fifth incorrect guess cannot unlock a link that has since locked”.

**OTP-03 — Medium: code accepted at its exact expiry.** At exactly ten minutes, actual verification succeeds; expected expiry rejection with signer row unchanged. Test: “OTP expiry is exclusive at exactly ten minutes”.

**OTP-04 — High: demo calendar reset extends a code beyond real validity.** Request a code while the demo clock is 30 days ahead, return it to today, then advance operational time601 seconds. Actual code still verifies; expected expiry rejection with row unchanged. Test: “returning the demo clock to today cannot extend an OTP beyond ten operational minutes”.

Implicated implementation: `src/domain/signing.ts` requestOtp/verifyOtp read-then-write challenge and attempts; expiry uses shifted `ctx.clock.now()` and `<` rather than rejecting the expiry instant. Test-only proxies pause completed real PostgreSQL reads and never alter their results; ten-second deadlines are cleanup, not ordering sleeps. Every barrier is released in finally.

## Additional reproduced defects and controls

**OTP-05 — High: a stale correct read consumes a newer resend.** Pause verification after its real old challenge read; request and deliver a different replacement code; release verification. Actual old verification succeeds, clears the replacement hash and verifies the signer without the new code. Expected old verification rejection, replacement hash retained, then the actual new delivered code verifies normally.

**OTP-06 — High: replacement code retains prior verification.** Verify one code, then successfully request a replacement. Actual new hash is stored and email sent but `otpVerifiedAt` remains set, leaving signing available without the new challenge. Expected either atomic refusal with unchanged row/outbox, or successful replacement that requires new verification. No UI-specific resend policy is invented.

**OTP-07 — Medium: provider rejection strands the prior delivered code.** After a successful first request, a fake provider rejects a resend before accepting any transport. Actual signer hash changes to an undelivered new challenge, invalidating the sole delivered usable code. Expected prior row/challenge usable and one total accepted transport. Separate positive control simulates acceptance followed by lost acknowledgement: the actual accepted challenge remains usable with one transport, so an arbitrary exception is not interpreted as proof of non-delivery.

**OTP-08 — High: signer token traverses a foreign envelope.** Keep own firm-scoped signer/token and own task, but replace envelope.firmId with a foreign firm. Actual public view returns company/signer context; OTP request sends; correct verification changes the signer. Expected all three operations reject without state/mail change. The missing envelope firm check is distinct from normal invalid-token rejection. No foreign/customer data is used.

**OTP-09 — Medium: signed link can still consume outstanding verification.** Model a terminal signing decision after a code was requested. Actual `verifyOtp` verifies and rewrites consumed-link state; expected signed link rejects atomically. Request on a signed link, and both request/verify on a withdrawn envelope, already reject as positive controls.
