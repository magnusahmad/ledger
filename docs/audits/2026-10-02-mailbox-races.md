# Area 2: observed mailbox replies and approval races

Original reporter: intake_audit. Product baseline: `822686c`. Isolated PostgreSQL database: `harbourline_robust_verify`; deterministic fixture LLM and FakeMail only. No live mail or customer data.

## Reproduced defects

**MBOX-01 — High: stale pending withdrawal overwrites an active or completed human decision.** `recordMailboxReply` reads a pending proposal and later writes `superseded` without checking its current status. Real query barriers reproduce both cases: approval claims and pauses after its committed delivery-start marker, or staff complete the send outside Harbourline. Resuming the old mailbox snapshot overwrites `processing`/`approved` with `superseded`, changes the original message's evidence, and creates an unnecessary follow-up. Expected: only a successful current-pending withdrawal may modify the message and create a replacement. Active approval must retain its owned snapshot and recover safely; completed outside delivery must retain its invoice/task history with no duplicate card.

Regression names: “a stale pending withdrawal read cannot overwrite a claimed approval or create a duplicate follow-up”; “a stale mailbox withdrawal cannot overwrite an approved completed-outside decision or create a duplicate follow-up”. Implicated: `src/domain/mailbox-replies.ts` pending findFirst → unconditional proposal/message updates.

**MBOX-02 — High: a known committed manual reply does not stop delivery of the now-stale approved message.** Pause approval immediately after the real `mail_delivery` prepared→sending update commits, before `deliverPrepared` begins its transaction and execution fence. Record and commit a manual mailbox reply on the same conversation, then release approval. Actual: FakeMail transport count is **1**, the old action completes. Expected: transport count **0**, delivery remains unsent, invoice draft and tasks at send, and a visible recovery/fresh-review path preserves the human-approved snapshot.

Regression: “a manual reply committed after approval claim but before the delivery fence blocks the old approved send”. Implicated: `src/domain/approval-execution.ts` facts omit observed manual reply history; `src/domain/mail-delivery.ts` delivery fence.

**MBOX-03 — Medium: stale pending evidence refresh rewrites a completed approval.** A mailbox reply in a separate conversation reads the firm's pending send cards, then pauses. Approve the original request completely, then resume the list's evidence update. Actual: the completed proposal payload acquires new `deliveryEvidence` from a stale pending read (`uploadLinkFound: true`, etc). Expected: a refresh may update only a currently pending card; the completed title, payload and encrypted approved snapshot must remain unchanged. Regression: “a stale pending evidence list cannot rewrite the payload or title of an approval completed while that list was paused”. Implicated: `src/domain/mailbox-replies.ts` pending list → unconditional evidence UPDATE.

**MBOX-04 — Medium: task history records unapproved draft recipient and subject instead of the approved sent receipt.** Strengthening the accepted-receipt overlap with explicit staff recipient, subject and body edits reproduces an incorrect activity entry. Actual transport and durable message contain `approved-recipient@kbtrading.example` / `Reviewed office instructions — 辦公室变更`, while `message.sent` says `director@kbtrading.example: Re: Office move`. Expected: every linked task's sent event names the exact approved actual recipient/subject. Implicated: `src/domain/handlers.ts` retains pre-send `m` for event/chase summaries. Actual focused red: **1 failed, 5 skipped, 5.80 seconds**, log `/private/tmp/harbourline-robustness-20261002/verify-area2-history-red.log`. All prior receipt, journal, transport-count and task/invoice completion assertions pass before the incorrect history assertion.

**MBOX-05 — High: a known reply committed during provider reconciliation is missed before transport.** Real client `ask_question` flow has a send proposal with no request/invoice/tasks, avoiding task foreign-key locks that could serialize the mailbox commit. Pause the already-successful unchanged FakeMail `not_sent` lookup response after the execution fence, commit a same-conversation manual reply, prove its sent/viaMailbox row is visible through the independent original DB context, then release provider reconciliation. Actual transport count is **1**, expected **0**. Regression: “a manual reply committed while authoritative absence reconciliation is awaited prevents transport of the stale approved question reply”. Requires unsent journal, visible unapproved decision and unchanged invoice/request rows on rejection. Implicated: `src/domain/mail-delivery.ts` executes its fence before an awaited reconciliation and does not recheck newly observed history immediately before `mail.send`. Focused baseline red: **1 failed, 6 skipped, 1.57 seconds**, actual test272ms, log `/private/tmp/harbourline-robustness-20261002/verify-area2-reconciliation-red.log`. This is a committed, visible observation before transport, not an unobserved external-mail race.

## Fixer candidate and observed boundaries

Before implementation, the failing business rules were announced: stale pending withdrawal must not overwrite a claimed/completed approval; a manual reply committed before delivery must block stale content; completed approval evidence and actual sent history must remain immutable and accurate. Own isolated reproduction: initial four interleavings **3 failed/1 passed, 10.00s** (`fixer-area2-mailbox-red.log`). The actual approved-recipient/subject task-history assertion reproduced separately: **1 failed/5 skipped, 5.61s** (`fixer-area2-receipt-log-red.log`). The provider-reconciliation gap also reproduced against the first candidate: **1 failed/6 skipped, 1.51s** (`fixer-area2-reconcile-gap-red.log`).

Repair: withdrawal claims only a still-pending proposal and mutates its draft/replacement only when that conditional update succeeds. Evidence refresh similarly cannot rewrite processing/completed approvals. The encrypted approval capture now retains firm-scoped manual Sent history IDs independently of the existing facts hash. A changed known reply blocks transport; confirmed journal acceptance instead permits the original local completion. Read-only provider reconciliation runs before acquiring the source conversation lock, then the conversation is held before the proposal/task/invoice fence and through actual transport. This serializes captured mailbox observations with delivery without transferring new wording into the old approval. Older captures with no history field require fresh review when existing manual history cannot be established as approved. Task and reminder history uses the actual sent receipt.
