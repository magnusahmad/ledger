# Decisions log

Decisions made during the claude.ai design phase (September 2026), newest last.

1. ~~**Build in-house, then sell as SaaS.**~~ Superseded by #17. The founding firm is customer zero. Migration from existing systems (CSA Expert, spreadsheets) must be close to seamless.
2. **Modernise, don't clone CSA.** Organise around work (tasks driven by playbooks) and clients, not just records. Registers update as a consequence of completed tasks.
3. ~~**Personal WeChat stays.**~~ Superseded by #18. No WeCom migration, no unofficial automation. WeChat is descoped to paste-in for v1; the app handles "what to do next", staff handle "what did the client mean", with AI suggestions they can override.
4. **Multi-select requests.** One client message can produce several tasks with one combined reply and one invoice.
5. **Invoice first by default.** The invoice goes out with the information request; work starts on payment.
6. **Credit terms are allowed.** Per client (usual terms) and per request. On credit, the payment step is skipped and the invoice is tracked for ageing, overdue flags and reminders.
7. **Bank integration.** Airwallex and HSBC, checking automatically and matching by invoice number and amount; manual override retained.
8. **Editable invoices at the prepare stage.** Invoice number and prices are inline-editable with live message updates. Post-send changes will need an explicit, logged "Revise invoice" (not built).
9. **"Matters" renamed "Tasks".**
10. **Two centres of gravity.** Today (my work) and Clients (find a client, act for them). New request is launched from the client page.
11. **Staff assignment.** Each client has a staff member in charge; tasks default to them and can be reassigned. Today shows only the signed-in user's work.
12. **Client page tabs** modelled on CSA's Client Master File but modernised: Overview, Company, Shares and members, Officers and controllers, Records and filings, Contacts, Billing.
13. **Reminders go to the billing contact in their language.**
14. **Credentials are vault-held and never displayed** (CSA shows the CR e-Registry password in plain text; we won't).
15. **Visual design.** Neutral light palette, low clutter, IBM Plex Sans + Noto CJK, red seal stamp only for deadlines within 30 days.
16. **Playbooks need an owner.** Keeping forms and rules current as the Companies Registry changes them is a permanent role, not a one-off build task.

## 29 September 2026, build requirements session (owner)

21. **Build the end-to-end investor demo and close the CSA parity gaps.** Scope and plan in `docs/BUILD_SPEC.md` and `docs/MILESTONES.md`.
22. **Product LLM runs on OpenRouter, `google/gemini-3.8-flash`, for now.** Used only by the product at runtime (intent, extraction, translation, drafting). The build, coding agents and reviewer agents never use OpenRouter. Replaces `PRODUCT_SPEC.md` §8's Anthropic API default for this phase.
23. **Client intent is understood only by the LLM.** No keyword rules or classic NLP for "what the client means"; the prototype's `triggerKeywords` are replaced by a natural-language `whenToUse` per playbook. The playbook flow that follows can be rule-based, but the agent re-reviews requirements whenever task data changes (spec §4.2).
24. **Single tenant, single user for this build.** Every table keeps `firm_id`, but RLS policies, login and roles are deferred. This is a deliberate, temporary exception to the `AGENTS.md` non-negotiable; RLS must land before any second firm or design-partner data. Residency and PDPO also deferred.
25. **Email: Gmail API (OAuth) primary, AgentMail fallback,** behind one mail interface; Outlook (Graph) later.
26. **Runs on the founder's laptop.** Next.js, worker and Postgres (Homebrew) locally; inbound email and bank deposits are polled, so no public URL.
27. **Airwallex: bank-transfer deposits to the Global Account, matched on invoice number and amount.** The demo uses the sandbox deposit simulation.
28. **Xero through the official Xero MCP server,** with Harbourline as MCP client doing deterministic invoice and payment sync. The LLM doesn't decide accounting writes.
29. **Unknown senders become prospects** with the onboarding playbook added to their request.
30. **In-house e-signature** (email OTP, stamped PDF, audit certificate) behind a provider interface.
31. **Jurisdictions: Mainland China, Macau and Taiwan get records plus core playbooks;** offshore (BVI, Cayman, Seychelles) later. Companies Registry forms are the official fillable PDFs filled in. Screening via OpenSanctions. Demo firm identity: Caine Road Corporate Services Limited (fictional). Automation: internal steps run automatically; every client-facing send, register change and filing record needs a human click.
32. **Xero invoices are approved with one direct API call.** The official Xero MCP server (v0.0.17) creates invoices as DRAFT and has no tool to approve them, but Xero only accepts payments against AUTHORISED invoices. Harbourline therefore uses the MCP server for contacts, invoices, lookups and payments, and calls the Xero API directly only to set an invoice to AUTHORISED, with the same credentials. Revisit if the MCP server adds invoice status updates.
33. **Product model runs with reasoning effort "low".** At the default, Gemini 3.8 Flash spent up to 7,000 reasoning tokens on some intake calls (up to 166 s). At "low", the 13-scenario live eval is 13/13 with a median of 11 s per message end to end (intake plus draft). Configurable with `LLM_REASONING`.
34. **Staff screens show only what the team needs to do the work.** Demo and measurement instruments stay out of the working screens: no time-saved panel on tasks (the Time saved report lives under Settings → Reports), no "Live" or "mail checked" indicators (pages update silently and only show "Reconnecting…"), no manual "check mail/bank now" buttons (the worker polls), and no Demo panel link (it stays at `/demo`). Stored codes (`tc`, `HK`, `sent`, `seed`, ISO dates) are always shown as words and dates. The client upload link is one form with a single Send button, not a save button per item. A prospect first known only by the sender is named after them (flagged as provisional) rather than "(new prospect)"; onboarding tasks are not titled with the instructing person checked for KYC.
35. **Requests can be started manually.** New request has two modes: "From a message" (pasted text, read by the product model) and "Start manually" for instructions taken in a meeting or on a call. Staff choose playbooks and enter what they already know (person, effective date, details); Harbourline creates the same tasks and invoice as the email path. By default it drafts a confirmation ("thank you for meeting with us…") with the invoice and upload link for approval. If staff choose not to send one, the send step is recorded as agreed in person and the invoice is issued for them to hand over; nothing goes to the client. Manual requests are logged as taken in person by staff, never as client messages. Opened from a client record, the client is fixed. One-off (custom) requests still go through the message path, which plans them.
36. **Replies sent straight from the shared mailbox are captured.** Phase 1 uses one shared firm mailbox. Harbourline reads the Gmail Sent folder as well as the inbox; mail it sent itself is recognised by message ID and skipped, and anything else sent from the mailbox joins the thread as "Sent from the mailbox", so later reading has the full history. Such a reply withdraws any Harbourline draft waiting on that thread, so the client is never answered twice; if the withdrawn draft carried the invoice and upload link, a "Still to send" card puts it back on Today to edit. The product model reads the reply against the client's open tasks and suggests matching updates (item not needed, value confirmed, cancel, start new work, note) as one card; nothing is applied until staff approve, and they can untick individual changes. Suggestions that point at another client's task, a closed task or an unknown item are dropped. Outlook (Microsoft Graph, Inbox and Sent Items) is next.
37. **Off-platform steps and holds.** Staff can add an off-platform step to any running task (what, who it waits on: us, the client or a third party; due date; follow-up date; optionally "must be done before" a later playbook step, which the engine enforces), and it can only be closed with proof: a note, a reference or a document. A task can be put on hold with a reason, who it waits on and a follow-up date; while held it doesn't move on by itself. Today's "Outside the platform" section lists both, due follow-ups first, and "Followed up" records the chase and sets the next date. Held tasks still accept staff approvals.
38. **Third parties are not clients.** Banks, law firms, auditors, officials, notaries and outgoing secretaries are kept as third parties linked to tasks, not on the client list. Their email is logged on their open tasks (or raised as "Needs a look" if none) and is never read as a client instruction, so it can't create prospects or drafted replies; an "ignore" sender is recorded and nothing else. "Not a client" on an email thread saves the sender as a third party (or to ignore) and, if Harbourline had made a prospect from their email, closes it: open tasks cancelled, draft invoices voided, pending drafts withdrawn, client archived. A real client's contact can't be tagged. Off-platform steps and holds can name the third party they wait on.
39. **Costs after invoicing never rewrite an invoice the client has.** "Add a cost" on a task (late fee, fine, court fee, stamp duty, as a disbursement or a fee) goes on the request's invoice while it is still a draft. Once that invoice has been sent or paid, the cost goes on a new additional invoice linked to the same request, and a covering email ("we have paid the following on your behalf", no upload link) is drafted for approval with the PDF attached. The additional invoice is matched to payments by its own number and doesn't hold up the task's payment step.
40. **Chasing and escalation.** When a task waits on the client for information or signatures, the worker drafts a reminder for approval after a set number of days since the client was last asked or last did something (default 5), then again at a set interval (default 5). It escalates when the statutory deadline is within a set window (default 14 days) or after a set number of reminders (default 3): the card is marked as an escalation, the email says the deadline is close, and "Call the client" is added to the task as an off-platform step due today. Held tasks and tasks with nothing outstanding are never chased; at most one reminder waits per task. The rules are firm settings, edited in Settings. Invoice reminders are unchanged.
41. **Enforcement letters start work, not just a notice.** The mail-room model now recognises Companies Registry enforcement: a late-filing notice, a warning letter or a summons, with the reply-by or hearing date, form, reference and any amount. Instead of the plain "a letter arrived" email, Today shows one card to start the matching playbook (hk.lateFiling, hk.warningLetter, hk.prosecution). Starting it opens the task with the letter's date as a hard deadline (new deadline kind `letter_date`), attaches the scan to the task, ticks the reference and overdue filing, and drafts an email explaining the letter with the scan and invoice for approval. "Only tell the client" falls back to the plain notice. The three playbooks are data, marked for company secretary (and, for court work, solicitor) verification. `npm run db:migrate` now also loads new playbook versions into an existing database.
42. **Demo clock for recordings.** The demo panel can jump the app's "today" ahead 1 to 60 days at a time and immediately runs the reminder, escalation and invoice-reminder checks as of the new date; "Back to today" and "Reset demo data" return it. The offset is stored in the database so the web app and worker agree, and every page render and worker tick picks it up. It's a demo tool only: on by default except in production builds, controlled by `DEMO_TOOLS=0/1`. Records created while ahead keep their future dates, so reset the demo data after recording; approval timing corrects for the offset.
43. **Staff can mark sending done by any medium.** Reply review and the current sending or confirmation step have a neutral "Mark done" action with an optional note. For a request, staff confirm delivery of the invoice and request details: the invoice becomes sent, linked sending steps advance under their existing payment terms, and pending duplicate drafts are withdrawn. This remains available from the task after a draft is dismissed. Every later sent email is checked for the exact bytes of a generated current invoice PDF and the request's upload URL, including emails in another thread to the intended recipient; filenames alone do not count. Invoice and link evidence can come from separate emails. Generated PDF snapshots retain their financial fingerprint so old prices do not count. Evidence is shown for staff confirmation and never automatically completes sending. Other media and PDFs generated before snapshots were retained use the same staff override. This supersedes #36's assumption that an external mailbox reply necessarily omitted the invoice and upload link.
44. **Hong Kong fees priced like traditional local firms.** Playbook fees were well above market (e.g. HK$1,800 to appoint a director). They are now set against price lists published in Sept 2026 by traditional local secretarial and accounting firms (會計妹, 信諾會計, 智明會計, Kams Business Services), not online platforms, with government fees charged separately as disbursements. Director, secretary and address changes HK$500–800, name change HK$1,500, share transfer HK$1,380, allotment HK$1,200, annual return HK$600, deregistration HK$3,000, summons response HK$2,000. Each changed playbook got a new version, so open tasks keep the price they were quoted. Mainland China, Macau and Taiwan fees are unchanged pending a benchmark. A test holds the Hong Kong fees under ceilings taken from those lists. Company secretary to confirm.
45. **Overdue and due-today deadlines count as "Needs you".** A deadline that is overdue or due today and not yet started now sits under Needs you on Today, and counts towards "N things need you" and the Today badge. "You're all caught up" only shows when nothing needs staff. Later deadlines stay under Upcoming deadlines.
46. **Companies Registry filing through TPSI (scoped, not built).** Earlier docs said the Companies Registry has no filing API. That was wrong: its Third Party Software Interface (TPSI) lets secretarial software submit specified forms, and CSA Expert uses it for ND2A, NR1, NNC1, NNC2 and NSC1. Until Harbourline integrates it, staff key forms into e-Registry and record the reference, which leaves Harbourline behind CSA on filing. Plan: a `FilingProvider` adapter (TPSI plus a fake), a "Submit to the Companies Registry" approval on the filing card, the acknowledgement recorded automatically, credentials in the vault, one e-Filing account per firm. Starts with ND2A and NR1. Blocked on the firm registering an e-Filing account and TPSI access to obtain the specification. Scope in `docs/CR_TPSI.md`.
47. **Interrupted approved work remains an explicit recovery action.** A proposal is processing after a human click and becomes approved only when its business effects complete. Five-minute ownership leases use operational time, independent of the demo offset. Local handlers and their final approval record commit together; deliberate stale-preview invalidation is preserved outside a rolled-back business transaction. Delivery attempts retain encrypted exact recipients, wording and attachment bytes, a stable RFC Message-ID, the connected provider/sender and acceptance evidence. A lost response is reconciled with positive provider evidence; Gmail search absence and providers without reconciliation remain unknown. Unknown mail is never automatically resent. Staff can check and resume an unchanged approved action, or explicitly record a mailbox check and close it for a fresh human preview with a new draft/delivery identity. The original uncertain journal remains evidence. All signing recipients and stable personal links exist before the first invitation is sent. Jobs hold a database row lock across local effects and completion, reclaim abandoned claims and retain visible accounting failure evidence. Stored bank/mail batches resume idempotently; metadata for attachments commits as a complete batch, while unreferenced storage bytes after interruption may remain for later cleanup.
48. **Scope changes preserve delivered financial and statutory history.** Before a request is sent, staff-approved added or replacement work refreshes its full draft quote, including playbook statutory fees, and its sending approval. Once the original quote is issued (or a free request has already been sent), new services use a separate linked request and draft invoice with the normal human sending and payment gates. Staff can edit that new quote; Harbourline never invents a refund, credit or offset against the original fees. The original invoice, payments, approved wording and PDF remain evidence. Provider acceptance freezes the approved invoice PDF even if local issue bookkeeping is interrupted; merely closing a recovery card is not proof of non-delivery. An original-store authoritative non-delivery check plus explicit staff closure permits a fresh draft correction. A recorded filing or approved register change, and a completed task, lock the original task's facts and signed history. Staff start separately reviewed corrective work instead of using ordinary amendment or cancellation to rewrite that source; no legal correction form is inferred. Before filing, ordinary changes can still rebuild preparation and withdraw old signing links. Person-scoped public submissions retain the person context rendered with the form and reject stale context before storing files or facts; reloading the same request link provides the current context.

49. **Statutory particulars belong to each company's dated approval history.** The working person/contact profile remains available to existing CRM and collection callers. Register and document views resolve a separate company/person baseline and sparse, effective-dated approved field changes; an approval for company A does not update company B's statutory particulars. Backdated changes carry through later unrelated-field updates, and a later explicit update of the same field wins. ID numbers and residential addresses stay encrypted in both baselines and patches. Existing references receive the currently known baseline at migration, and new officer/member/controller references are enrolled before later profile changes. This preserves known facts prospectively; it cannot reconstruct values overwritten before history existed. Officer/controller periods may be adjacent but cannot overlap for the same company/person/role. A stale register preview after recording a filing supersedes that card and prepares a new human register review without regenerating or withdrawing its signed/filed source. New share movements retain a persistent causal order within each effective date, independent of clock ties and random identifiers; migration retains prior observable legacy order and does not infer lost insertion evidence. Explicit share-class currency is retained, conflicts or missing new-class currency require review, and company/firm ownership is checked.

50. **Edited workflows must match supported engine capabilities before publication.** Repeated generation and confirmation gates are currently refused with an explanation before saving: use separate reviewed tasks for separate packs or completion messages. The `personIsNew` requirement condition is likewise refused until reliable new-person provenance exists; it must not silently demand identity documents from an existing selected person. Optional items, supported client/CDD conditions, repeated manual/collection steps and required event-date waiting remain supported, and running tasks keep their pinned versions. Where a definition includes a document signature gate, it must precede filing. A proof step ordered before the current filing or register gate blocks that actual approval until staff complete the proof; a hold alone still permits staff approval under #37 and defers progression until release. These are software capability and evidence guards, not new statutory rules.

51. **Email intake has explicit authority and planning gates.** An unknown sender interpreted as a prospective customer first produces a confirmation card showing the source enquiry and proposed work. Staff must confirm before Harbourline creates the prospect, tasks, invoice or reply; confirmation prepares work and does not send it. This supersedes automatic prospect creation in #29. Only instructing sender records (or a client explicitly selected in staff paste/portal intake) supply existing-client context; reply-thread headers and company names in email bodies confer no authority. Custom work always goes through planning, even if the model returns a direct custom start, and neither sending nor recording delivery can bypass plan approval. Appointment intake may select an existing shareholder/person; a new appointment is not necessarily a new identity. Full ISO/Chinese dates in quoted evidence receive consistency checks; inconsistent or omitted structured dates go to staff, and accepted date changes synchronize the checklist, extracted facts and computed deadline. Review outputs are checklist deltas, not replacements. Equivalent contact formatting is not a conflict. Reply facts state the proposed/approval status separately from payment terms; the application renders localized financial wording and exact bank details at the model's invoice placeholder. These guards reduce specific observed errors, but neither they nor the prompts guarantee complete or correct interpretation. The matched Gemini rerun is recorded under `eval/results/emails-eval-2-gemini-fixed/`.

52. **Email preparation distinguishes advice, quotations and instructed work.** Intake retains the service, supplied fields and requested phase separately. Advice does not create work. A quote prepares proposed scope, requirements, assumptions and prices for human review, including custom planning when needed, without opening service tasks or an invoice. Sending that quote remains a human approval; it does not start the service. An explicit preparation instruction retains the usual task, invoice and approval flow even when quotation approval is also requested. New prospects still require staff confirmation first. Request instruction notes persist in task evidence and reach initial drafts and redrafts; a planned resolution date is not an actual statutory event date. Cancellation wording is rendered by the application from current firm-scoped task status, distinguishing a request from completed cancellation. Quote prices and scope are rendered from proposed underlying-service facts, including a monthly, annual or one-off fee basis; preparing a quotation is not itself a chargeable service. Credit terms cannot be rewritten as payment before work. Questions receive only relevant task/deadline facts; when no approved answer is available, the application drafts a localized holding response for staff instead of supplying unrelated deadlines or invented advice. A requirement-review result that marks a compound item incomplete survives application of extracted fields, and deterministic contact checks require both email and mobile. Supplied contact values remain visible in reply facts while only missing components are requested. These are specific wiring and prompt corrections supported by regressions, matched Gemini runs and focused draft checks (`eval/results/emails-eval-3-gemini-context-final/`), not proof of general reliability; statutory rules, advisory answers and proposed custom pricing still require staff judgment.

53. **UHY-ASK pilot runs as a light package on the firm's own systems.** On 6 October the owner directed us to put CTC/CDD results ahead of cloud deployment, server VM setup and legacy-data migration tooling; later that day the owner chose the lighter local footprint over a bundled desktop product. The firm's systems stay the record: Access, DN, CSA, Xero, the shared drive and the mailbox remain sources, and the pilot writes its results back into them (evidence filed into existing client folders, Outlook drafts, and a status workbook and review log on the firm's share that staff can read without our app). Nothing the firm needs is stranded if the pilot is switched off. Evidence files are referenced by path and fingerprint, not copied into a separate store. Several staff need it, so one backend process runs on one always-on office machine (preferably the server behind the shared drive) and staff use it in a browser over the office network only, with sign-in; the database file is never opened by several copies over the share. Local state uses an embedded database owned by that process (PGlite first, to reuse the Postgres schema; to be verified in the connector spike) with no separate database service, job queue or self-managed backup system; the state file and the mirrored review log on the firm's share are backed up by the firm's existing backups. Every row still carries `firm_id` so pilot data can later move into Harbourline. A single-firm installation on the firm's own machine provides the separation between firms that RLS provides in a shared deployment; this is a deliberate exception like #24 and does not relax RLS for any shared deployment. CRV maintains the installation remotely with the firm's agreement rather than building self-service update or administration tooling. The mail connector is Microsoft Graph if the mailbox is Exchange Online, otherwise classic Outlook COM (to be confirmed with the firm). The firm's requirement is that the client-records database stays on its own server; sending documents to the product model for reading and drafting (#22) is acceptable to it, including outside Hong Kong (confirmed by owner, 6 October). Scanned courier post goes to one watched folder; Harbourline reads, classifies and files each document into the client's folder, automatically only when it matches exactly one client, after a two-week period in which staff confirm every filing to measure accuracy. Staff review of findings and completion, and staff sending of drafts, still apply. Scope, open questions and acceptance tests: [UHY annual return and AGM pilot](UHY_AR_AGM_PILOT.md). This is an implementation direction, not a claim that the package or connectors exist.

54. **CDD is a first-class Harbourline module.** Confirmed by owner, 6 October: every licensed TCSP must carry out customer due diligence, so CDD is core platform scope for every CRV-owned firm, not pilot-only code. The original design treated KYC as a status field on a person and a step kind inside playbooks. CDD needs its own model: people separate from companies, with staff-confirmed links across companies; a per-person and per-company evidence file assembled from email, files, scanned post and client uploads; checklist items by role (director, shareholder, significant controller, beneficial owner, person purporting to act, corporate party) driven by firm-configurable policy data, like playbooks; distinct states for evidence received, evidence assessed and CDD complete, with a recorded human approval; risk rating, periodic review dates and ID-document expiry; and backlog reconstruction from historical evidence where an unsearched or failed source never counts as "not supplied". Certifier rules, address tests, review frequencies and screening are firm policy needing company-secretary verification, never hard-coded. The UHY-ASK pilot (#53) builds this module's domain code in the main codebase; only the connectors and the local packaging are pilot-specific.

55. **UHY-ASK pilot starts with annual returns and AGMs; CDD runs inside that cycle.** Decided by owner, 7 October, after Allan said UHY is refreshing all CDD by hand before the pilot and sees annual returns, AGMs and Registry filings as the routine work that matters most. This supersedes the CTC/CDD-first scope recorded on 6 October; the packaging in #53 and the CDD module in #54 stand. The pilot reads CSA (read-only) for officers, members and particulars, prepares the client confirmation request, proposes changes from replies for staff approval, generates the NAR1 with the existing generator (falling back to CSA where it can't), drafts AGM papers from the previous year's document and the audit report, and tracks each company to filed. It does not write to CSA, file electronically or replace CSA. CDD enters through the annual-return request: companies without a recorded cleanup completion, new people, expiring IDs and periodic reviews. Coe or Ruby prepare and Allan signs off, and outstanding CDD does not block the annual return unless the firm decides otherwise. Registry changes are checked by staff with an assisted step (UHY declined e-Monitor on 9 October); the portal is never scripted. Following UHY's process (9 October), nothing is sent to the client until staff record that payment is confirmed, and AGMs default to written resolutions, with UHY's deferral wording when audited accounts are late. Scope and tests: [UHY annual return and AGM pilot](UHY_AR_AGM_PILOT.md).

56. **UHY pilot: modules switched per installation, templates for AGM papers, and oversight from recorded defects rather than model confidence.** Decided by owner, 23 October. Harbourline stays one codebase and schema; each installation lists its modules, switched-off modules are not loaded, and an installation never falls back to a fake adapter or shows demo tools. CSA's particulars are copied read-only into Harbourline's register tables, marked as from CSA, so the dormant modules (other Registry forms, CDD) can later run on the same data. AGM papers are generated from firm templates plus per-company standing clauses confirmed once, with the model limited to extracting facts staff confirm; it does not edit last year's Word document. Our evaluations showed the model is consistently confident even when wrong, so no routing, review skip, automatic action or warning depends on its self-reported confidence. Each AI task starts in shadow mode with every output reviewed by staff; edits, rejections and additions are recorded automatically as defects and turned into fictional test cases. A task leaves shadow mode only on its defect record (confirmed: at least 30 real items, no missed items in the last 30, under 1 in 10 edited or rejected), a missed item puts it back, and the human-approval gate still applies throughout. Details: [UHY annual return and AGM pilot](UHY_AR_AGM_PILOT.md), [implementation plan](UHY_PILOT_PLAN.md).
